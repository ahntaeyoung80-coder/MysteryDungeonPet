## 2. 확인한 원인과 근거

### 직선 대신 대각선 — 기존 실행 기록에서도 확인

- `src/core/exploration.cpp:75,94`의8방향 BFS는 직선·대각선 비용이 모두1이다. `S,SE,E,NE,N,NW,W,SW` 순서로 처음 방문한 부모를 고정한다. 같은 걸음 수에서 직선/짧은 실제 거리/적은 방향 전환을 우선하는 기준이 없다.
- 이미 커밋된 실제 Windows `docs/validation/2026-10-15-companion-windows/follow.csv`에서 목표 아이템(9,5)까지 `(5,5)→(6,6)→(7,7)→(8,6)→(9,5)`가 확인됐다. 직선4칸도 가능한 공개된 두 방 fixture다. 기존 검사는 반경·합법성만 검사해 이 경로를 통과시켰다.
- 추가 요인: `companionFollowTile`/`playerOccupancy`의 결합 이동 마스크, 저체력 적 사거리 회피, 반복 감지 detour. 모든 대각선을 금지하지 말고 같은 목표에서 직선 우선/실제 거리/꺾임 기준을 정하고 필요한 회피만 허용해야 한다.

### 저체력의 한 칸씩 멈춤 — 구조상 후보 확인, 사용자 장면 시간 재현은 미완료

- 보행 자체는 HP와 관계없이400ms다(`MoveRecord`, `scheduleDungeon`, Motion). HP별 보행 속도 감소 분기는 확인되지 않았다.
- `lowHealth`/`mustRetreat`는 두 배우 중 하나의 저체력을 전역 도주 상태로 만든다. `afterCombatAction`의350ms 대기, 인접 적 재조우, Attack/Hurt 완료 대기, 이동/회복으로 이미 소비한 동료 행동권 때문에 따라갈 수 없어 발생하는 Wait400ms를 확인해야 한다.
- 저체력 적 추적 이동은 이미 주인공과 같은400ms에 처리하는 분기가 있다(`gameplay.cpp:623`). 이를 다시 구현했다고 끝내면 안 된다. 새 party 상황의 실제 action/start/deadline/Wait/공격 완료를 구분해 간격을 측정해야 한다. 사용자 해당 snapshot은 이번에 확보하지 않았으므로 특정 지연 하나를 확정 원인으로 주장하지 않는다.

### 포위되면 귀가 — 잘못된 종료 경로가 남아 있음

- `exploration.cpp:514`의 plan은 동료 합류 불가·점유·안전 마스크로 목표를 잃을 수 있다. `advance:572`는 `target<0`이면 `ReturnedHome`을 반환하며, `gameplay.cpp:690`이 귀가로 연결한다. 반복 감지 자동 귀가를 없앤 이전 수정과 별개의 경로다.
- `gameplay.cpp:327,481,492,598,662`는 저체력 때문에 전투 진입/동료 전투를 회피한다. 포위됐을 때의 ‘도주 불가→전투’ 전환이 없다. 사용자 HP1 장면의 정확한 실행 재현은 미완료이나 해당 동작을 만들 수 있는 코드 경로는 확인했다.

### 늦은 지원·양쪽 적 정지 — 단일 조우 중심 스케줄러의 한계

- `GameplayState`에 `enemyInstance/enemyHits/hit/damage/enemyTargetsCompanion`가 한 세트뿐이다(`exploration.hpp:130~146`). Windows도 현재 적용 `enemyAnimator_` 한 개를 사용한다. 적별 이동 Animator가 있다는 것과 독립 전투 지원은 다르다.
- `afterCombatAction:476`은 주인공→동료→현재 적의 순서이며 각 단계350ms를 둔다. 동료의 평상시 추적 이동도 그 라운드 행동권을 소비한다. `CompanionTurn`은 같은 `enemyInstance`만 공격/접근하고 접근 후 즉시 공격하지 않는다. 따라서 주인공 공격 뒤에야 돕거나 반대편 적을 독립적으로 상대하지 못한다.
- 다른 미행동 적이 있더라도 현재 조우의 미소비 주인공/동료/적 행동을 먼저 처리한 뒤에야 전역 스케줄러로 돌아간다. `Faint→Victory→Explore` 역시 현재 조우 처리로, 모든 배우의 라운드 장벽이 아니다. 이 때문에 반대편 공격이 한 조우 종료까지 밀릴 수 있다.
- 전역 `mustRetreat`가 동료 전투도 중단시키고, `combatApproach:546`은 동일 방·주인공 반경1칸을 강제한다. `companionFollowTile:367`과 상태 검증 `exploration.cpp:684`도1칸 밖 전투/복귀를 허용하지 않는다.
- 후속 설계는 배우별 목표/행동/피해 확정·전투 완료 신호와 라운드 스케줄링을 함께 다뤄야 한다. 한 적이 죽어도 나머지 아군/적이 각자 행동하고, 라운드/적/배우 키로 중복 피해를 막는다. 저장 구조를 늘리면 형식 버전·이전 저장 읽기·중단/복원을 함께 설계한다. 기존 명중/피해와 이동 후 추가 공격 금지를 무심코 바꾸지 않는다.

### 방 중복 — 기존 검사 범위의 한계, 보고 자체는 미해결

- `layoutKey:14`는 전체 terrain 배열만 해시하고 `runId`로 범위를 나눈다. `enterFloor:283`은 같은 run의 완전히 동일한 지도만 거부한다. 다음날에는 새로운 Explorer/run/journal로 시작한다(`gameplay.cpp:313`).
- `generate:123`은 같은4슬롯·2~3개 방·가로/세로3~6칸 사각형을 재사용한다. 개별 방 크기/모양, 위치를 옮긴 유사 배치, 다음날/새 run의 반복은 금지하지 않는다. 새 run의 기본 seed도1이어서 수동 새 실행의 첫 지형은 반복될 수 있다.
- 기존 `entry_social_scene_tests.cpp:28~48`은 같은 run 전체 지형 완전 중복과 방 bounding box 겹침만 검사했다. 통로/카메라 때문에 같은 방을 다시 보는 문제와 시각적 유사성도 구별해야 한다. 사용자 보고가 어느 유형인지는 아직 미확정이다. 다음 점검에서 run/floor/mapSeed/room ID·bounds·terrain/camera를 묶어 확인한다.

## 3. 원본 자산·7층 자료 확인

원본 ROM은 읽기 전용으로 조회했으며 자산을 추출/교체하지 않았다.

- 녹색 켈리몬: **MD383 / sprite556 / 도감352**. 원본 Idle 프레임 주요색 `(95,183,39)`, `(39,135,0)`.
- 보라색 켈리몬: **MD384 / sprite554 / 도감352**. 원본 Idle 프레임 주요색 `(199,151,223)`, `(127,95,167)`. 두 색 모두 기존 `MONSTER/monster.bin`에 있고 신규 외부 입력은 필요 없다.
- 현재 `actors/asset-2`는 녹색이며 모든 적/우호 NPC가 같은 `enemyAssets_`로 그려진다(`windows/main.cpp:881,965`). 관계를 기준으로 녹색/보라색 자산을 선택하도록 추출 도구·표시·복원/방향·픽셀 검사를 같이 변경해야 한다. 원본 종 ID와 대표 몸체 선택은 혼동하지 않는다.
- 기본 `dungeon-0/exploration.mdpe`는3층, 이미 있는 `dungeon-15/exploration.mdpe`는7층이다. 보관 ROM HardcodedDungeons에서도 각각3/7층임을 확인했다. 던전15는 기존 원본7층 및 tileset12를 재사용할 수 있는 후보이며, 서로 다른 던전의 층을 출처 없이 복제/혼합하지 않는다.
- 기본 경로만7층 패키지로 바꾸면 `loadSnapshot(..., explorationPackage_->assetVersion)`의 기존3층 저장 버전이 달라져 복원이 실패한다(`windows/main.cpp:982`). 기존 저장의 출처별 로딩/진행 유지와 새 탐험의7층 적용 전략이 필요하다. 기존 저장 삭제를 정상 이행 방법으로 삼지 않는다.

## 4. 재개 순서·최소 완료 판정

1. 이 문서와 PROJECT_STATE를 읽고 fetch/HEAD 비교. 기존 코드/EXE의 CI 성공은 옛 명세에 대한 결과다. 새 보고를 해결했다고 간주하지 않는다.
2. 회귀부터 고정: 빈 방의 동일 행/열 직선, HP5/HP1 보행 간격, HP1 포위 시 귀가0회/전투, 통로 `적A–동료–나–적B`, 한쪽 적 처치 뒤 나머지 행동, 주인공 도주 중 동료 전투 완료→직선 복귀, 이 상태들의 매행동 저장/복원.
3. 배우별 전투/도주/추적/복귀 우선순위와 전역 라운드를 먼저 정비한다. 주인공과 동료가 서로 다른 적을 같은 라운드에 처리하고 적도 각각1회 행동하는지 검사한다. 실제 동시 애니메이션·완료 소유자·저장 피해 중복까지 확인한다.
4. 직선 우선·저체력 시간·막힘 전투/대기·거리 제한을 함께 연결한다. 동료 HP 숨김·녹색 우호/보라색 적·7층/기존 저장 호환을 적용한다. 방 중복은 유형별 검사와 해결 근거를 추가한다.
5. 변경 뒤 필요한 코어/Windows 검증·EXE/hash 갱신·원본 불변 확인 후 단계별 커밋/work push. 새 단계를 시작하기 전 ETA를 보고한다. **이번 문서화 턴에는 착수하지 않았다.**

남은 증거: 사용자 HP1 포위/저속/방 중복의 실제 snapshot·trace는 아직 없다. 현재 보관 자료만으로 확정한 것과 후속 실행 재현이 필요한 것을 위에서 분리했다. 이번에는 대규모 테스트/CI/빌드/배포를 실행하지 않았다.
