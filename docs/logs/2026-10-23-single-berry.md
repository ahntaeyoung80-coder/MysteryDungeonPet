# 배우마다 오랭열매 하나만 소지

사용자가 “열매는 한 번에 하나, 사용하면 없어짐, 팀원도 하나”를 확정했다. 이전에는 소모 검사가 통과했지만 재고 상한99를 허용한 규칙 자체가 잘못되어 있었다.

## 구현

- 오랭열매 전용 한도1을 추가했다. 다른 아이템의 한도99는 유지한다. 현재 상태 검증과 저장 쓰기는 오랭열매 0/1만 허용한다.
- 지급을 실제 획득 경계에 모았다. 빈 배우에게만 하나를 지급하고 legacy/독립 파티 후속 처리에서 다시 더하지 않는다. 둘 다 소지 중인 열매는 탐색 목표에서 제외하며 바닥에 그대로 두고 획득 이력·메시지를 만들지 않는다. 사용 후 빈 슬롯이 생기면 다시 획득할 수 있다.
- 둘 다 빈손이면 체력이 더 낮은 동료를 우선하고, 그 외에는 플레이어를 우선한다. 한쪽만 찬 경우 빈 배우에게 배분한다. 동료가 없을 때는 플레이어 슬롯만 사용한다.
- 물물교환은 플레이어 슬롯이 비어 있을 때만 한다. 찬 상태에서는 사과도 소비하지 않는다. 나눠 주기는 팀에 열매 하나를 남길 수 있을 때만 하고, 체력이 높은 배우(동률은 플레이어)가 자기 열매 하나를 준다. 팀의 마지막 열매는 보존한다.
- 사용 코드는 기존처럼 한 개를 소비해 최대5하트로 회복하므로 소지1 → 0이 된다. 무작위 출현·일반층 보장 공급·전투 피해는 변경하지 않는다.
- 기존 MDES1~18과 in-memory 복원은 2~99개의 누적 재고를 각자1개로 맞춘다. 0은 유지하고, 이전 유효 상한99보다 큰 값은 계속 거부한다. 과거 획득 기록·날짜·원정 진행·다른 아이템과 저장 형식은 보존한다.
- [검증 문서](../dialogue/ORAN_AUDIT.md)와 [출력 문구](../dialogue/DISPLAY_TEXT.md), 실행 안내·현재 상태·설계 결정을 새 규칙으로 갱신했다. 이전 3개씩/합계6개 소비 검사를 현재 소지 규칙의 근거로 삼지 않는다.

## 관련 검사와 실패 보정

최초 관련 ctest 8개 실행은 7통과·1실패(3.08초)였다. 실패는 `pet_event_combat_tests`의 배우당5개를 전제로 한 무조건 승리 기대였다. 한도1을 적용한 seed42 몬스터하우스에서 hp2/4·이벤트 Abandoned로 정상 퇴각했다. 제품 수치나 퇴각 조건을 약화하지 않았다. 검사를 seed42/1/7 × 몬스터하우스/공동전투로 바꿔 실제 승리와 빈 재고·낮은 체력의 안전한 퇴각을 모두 확인하도록 하고, 해당 검사만 다시 실행해 통과했다(0.44초). 이미 통과한 나머지7개는 반복하지 않았다.

최종 확인한 관련 코어는 다음8개다. 기존 ASan/UBSan 빌드를 재사용했다.

- `pet_berry_capacity_tests`: 실제 획득 경로의 단독/독립 파티 × 두 배우의0/1 조합8건, 가득 찬 팀의 바닥 열매 보존, 빈 배우 배분, 동료 없는 경우, 저장 복원 중복 방지, 공통 재고 API와 사과 규칙 보존, 기존 MDES18의99/2 → 1/1, 잘못된100 거부, 새 저장의 초과 재고 거부.
- `pet_gameplay_notice_tests`: 합계2개 소모와 저장 복원 후0 유지, 추가 부상에서 회복 없음, 실제 획득·알림·기존 저장 이관.
- `pet_event_stock_tests`: 한 개씩 소지 상태의 실제 나눔·예약·중복 방지·마지막 팀 열매 보존.
- `pet_event_combat_tests`: 거래·찬 슬롯의 거래 취소/사과 보존, 한 개 소지의 실제 승리와 퇴각·아군 공격 방지.
- `pet_playtest_balance_tests`: 기존 적 급소·공급·원정 선택 유지.
- `pet_survival_tests`: 체력·열매 사용·피난 경로 유지.
- `pet_variety_state_tests`: 기존 버전 복원·사용한 열매 미복구·생활 상태 유지.
- `pet_package_transition_tests`: 누적 원정·다음 날 두 재고 보존.

새 Windows x64 static Release로 `pet_berry_capacity_tests.exe`, `pet_gameplay_notice_tests.exe`를 Wine에서 실행해 통과했다. Wine의 기존 winedevice 경고는 있었지만 검사 자체는 정상 종료했다.
