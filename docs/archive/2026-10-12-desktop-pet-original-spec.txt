# Adaptive Desktop Pet v1.0 — Codex 개발 실행 명세

## 0. 프로젝트 목표

포켓몬 불가사의 던전 *탐험대* 시리즈의 원작 데이터와 기존 공개 구현을 최대한 재활용하여 Windows용 초경량 데스크톱 펫을 개발한다.

펫은 100~200px 크기의 작은 창에서 자율적으로 여러 던전을 탐험하며, 친구 포켓몬을 만나고, 아이템을 발견하고, 계단을 통해 층을 이동한다. 탐험 후 집으로 돌아와 휴식·수면·기상하고 다시 탐험한다.

사용자의 PC 활동은 펫의 생활 리듬과 반응에 간접적으로 영향을 준다. 사용자가 직접 조작하지 않아도 모든 기능이 동작해야 한다.

**구현 원칙**

1. 원작 재현을 최우선으로 한다.
2. 기존 오픈소스·게임 데이터·리소스 재활용을 신규 구현보다 우선한다.
3. 원작에 존재하는 규칙을 임의로 새로 설계하지 않는다.
4. 자료 조사·다운로드·변환·통합·테스트를 가능한 한 자동화한다.
5. 사용자에게 기술적 의사결정을 반복적으로 요청하지 않는다.
6. 단일 프로세스와 최소 의존성을 우선한다.
7. 검증되지 않은 기능을 구현 완료로 보고하지 않는다.
8. 원작의 규칙과 의도적으로 변경한 규칙을 구분하여 기록한다.

## 1. 원작 재현 기준

### 1.1 기준 게임

**최종 재현 기준: Pokémon Mystery Dungeon: Explorers of Sky (하늘의 탐험대)**

현재 보유하거나 테스트하는 어둠의 탐험대 데이터는 호환성 확인에 사용할 수 있지만, 하늘의 탐험대와 동일한 데이터 구조라고 가정하지 않는다.

원본 ROM이 필요한 작업은 사용자가 적법하게 보유한 ROM을 로컬에서 지정하는 방식으로 처리한다. ROM이 제공되지 않아도 공개 코드 분석, 테스트 데이터 기반 프로토타입, 변환 도구와 테스트 개발은 진행한다.

원작 ROM이나 상업용 게임 자산을 저장소 또는 배포 파일에 무단 포함하지 않는다.

### 1.2 원작에서 유지할 요소

| 구분 | 재현 대상 | 요구사항 |
|---|---|---|
| 던전 | 던전 종류·층 수·층별 구성 | 원작 ID와 설정 유지 |
| 맵 생성 | 방·통로·지형·특수 구조 | 원작 알고리즘 우선 |
| 출현 포켓몬 | 던전·층별 종류·가중치 | 원본 데이터 기반 |
| 아이템 | 던전·층별 종류·가중치 | 원본 데이터 기반 |
| 그래픽 | 타일셋·스프라이트·효과 | 원작 데이터 우선 |
| 애니메이션 | 방향·프레임·지속 시간·오프셋 | 원본 메타데이터 유지 |
| 이동 | 타일 이동·방향·경로 판단 | 원작과의 일관성 유지 |
| 계단 | 층별 배치·진행 | 원작 설정 활용 |
| 이벤트 | 아이템 발견·포켓몬 조우 | 원작 데이터에 연결 |

각 기능의 재현 수준은 `Exact`, `Equivalent`, `Approximation`, `Missing`으로 분류한다.

- `Exact`: 원작과 동일한 입력에서 검증된 동일 결과.
- `Equivalent`: 외형 또는 의미가 같지만 내부 구현 차이가 있음.
- `Approximation`: 일부 규칙을 근사 구현함.
- `Missing`: 미구현.

원작과 다른 계산·설정을 임의로 `Exact`라고 표기하지 않는다.

### 1.3 의도적으로 변경할 요소

다음만 원작 규칙의 예외로 허용한다.

- 전투 제거
- 등장 포켓몬을 우호적 NPC로 처리
- 포켓몬과의 간단한 인사·교류
- 아이템 자동 획득
- 던전 자율 탐험
- 탐험 후 집으로 귀가
- 수면·기상·재탐험 순환
- Windows 활동 감지에 따른 행동 조정

**전투를 제거한다는 이유로 원작의 출현표나 던전 생성 규칙까지 변경하지 않는다.**

## 2. 기존 코드 및 데이터 재활용 전략

### 2.1 필수 조사 저장소

| 우선순위 | 저장소 | 담당 후보 |
|---|---|---|
| P0 | `SkyTemple/skytemple-files` | ROM 파일 파싱·데이터 추출 |
| P0 | `EpicYoshiMaster/dungeon-mystery` | 던전 생성 |
| P0 | `PMDCollab/SpriteCollab` | 스프라이트·애니메이션 |
| P0 | `johanngan/pmd-bot` | 자율 경로 탐색·의사결정 |
| P1 | `pret/pmd-sky` | 원작 계산 검증 |
| P1 | `UsernameFodder/pmdsky-debug` | 원작 메모리 구조·함수 분석 |
| P1 | `SkyTemple/skytemple` | 게임 데이터 구조·추출 예시 |
| P2 | `audinowho/PMDODump` 및 엔진 하위 모듈 | 기존 PC 게임 시스템 활용 가능성 |

**조사 규칙**

1. README만 읽고 판단하지 말고 실제 코드·API·의존성을 확인한다.
2. 각 저장소의 라이선스와 의존성 라이선스를 확인한다.
3. 기능별 재사용 가능 여부를 실행 테스트로 검증한다.
4. 이미 존재하는 기능을 사전 조사 없이 새로 구현하지 않는다.
5. 원본 저장소의 구현을 불필요하게 수정하지 않는다.
6. 재사용할 코드는 가능한 한 독립 모듈 또는 명확한 어댑터로 연결한다.
7. 채택하지 않은 저장소는 제외 이유를 기록한다.

**최종 기술 스택은 조사 결과로 결정한다.**

TypeScript, C#, C++ 등 특정 언어를 미리 강제하지 않는다. 재현 정확도와 기존 코드 활용성이 동일할 경우 메모리·CPU 사용량 및 배포 단순성이 우수한 구성을 채택한다.

초기 조사에서 PMDO 전체 엔진과 독립 경량 엔진의 빌드 크기·상주 메모리·구현 비용을 비교한다. 성능을 측정하지 않은 상태에서 어느 쪽이 더 가볍다고 단정하지 않는다.

## 3. 원작 데이터 자동 수집·변환

### 3.1 목표

사용자가 던전별 포켓몬, 아이템, 등장 확률, 애니메이션 규칙을 직접 입력하지 않도록 한다.

### 3.2 자동 변환 파이프라인

```text
원작 ROM / 공개 리소스
       ↓
기존 파서·라이브러리
       ↓
전체 데이터 자동 추출
       ↓
ID 및 참조 관계 정규화
       ↓
게임용 데이터 패키지 생성
       ↓
데이터 무결성 검사
       ↓
데스크톱 펫 로딩
```

### 3.3 필수 데이터

**Dungeon Data**

- 원본 던전 ID·이름
- 층 수와 층별 설정
- 맵 생성 파라미터
- 지형·타일셋 참조
- 층별 포켓몬 출현표 및 가중치
- 층별 아이템 출현표 및 가중치
- 특수 구조와 환경 설정
- 계단·진행 관련 규칙
- 데이터 원본과 추출 상태

**Pokémon Data**

- 원본 포켓몬 ID
- 종·폼·성별 등 필요한 식별 정보
- 스프라이트 참조
- 초상화 참조
- 애니메이션 목록
- 방향별 프레임·프레임 시간·오프셋
- 데이터 유무 및 대체 리소스 표시

**Item Data**

- 원본 아이템 ID
- 표시명
- 그래픽 참조
- 던전별 등장 조건
- 출현 가중치
- 비전투 환경에서의 표현 방식

### 3.4 데이터 처리 규칙

- 전체 던전·포켓몬을 기본 대상으로 일괄 변환한다.
- 개발용 샘플 한두 개로 검증한 후 동일한 파이프라인을 전체 데이터에 적용한다.
- 원본 ID를 유지하며, UI 표시명과 내부 식별자를 분리한다.
- 가중치 데이터는 정규화 과정에서 임의로 균등 확률로 바꾸지 않는다.
- 출현표 참조가 깨졌을 때는 검증 오류를 기록한다.
- 일부 애니메이션이 없는 경우 해당 캐릭터만 기능을 축소하고 전체 앱은 유지한다.
- 캐릭터별 수동 XML 편집이나 스프라이트시트 분할을 사용자에게 요구하지 않는다.
- 생성된 데이터는 출처와 변환기 버전을 기록한다.
- 동일 원본·동일 변환기 버전에서 재현 가능한 결과를 생성한다.

ROM 데이터와 공개 팬 제작 리소스 사이에 차이가 있으면 **원작 데이터를 우선**하고, 대체 리소스 사용은 표시한다.

## 4. 던전 생성·탐험 시스템

### 4.1 던전 생성

원작 던전 생성 알고리즘을 재구현한 공개 프로젝트를 우선 사용한다.

입력:

```text
Dungeon ID
Floor Number
Random Seed
Original Floor Parameters
```

출력:

```text
Tile Map
Rooms / Corridors
Terrain
Stairs
Pokémon Spawn Data
Item Spawn Data
Environmental Metadata
```

지도 생성, 엔티티 배치, 전투 관련 생성 규칙을 구분한다. 기존 구현이 지도 생성만 지원한다면 아이템·포켓몬 배치는 원작 데이터를 읽는 별도 모듈로 연결한다.

같은 시드와 입력으로 원작 또는 검증된 참조 구현과 결과를 비교하고, 차이가 발생한 단계와 이유를 기록한다.

### 4.2 자율 탐험

사용자 입력 없이 이동 목표를 결정한다.

기본 탐색 우선순위:

1. 현재 층에서 접근 가능한 관심 대상 확인
2. 발견한 아이템·보물 수집
3. 우호적 포켓몬과 조우
4. 미탐색 영역 탐험
5. 탐험 종료 조건 충족 시 계단으로 이동
6. 다음 층 또는 귀가 상태로 전환

경로 탐색과 의사결정은 기존 PMD-Bot 등의 구현을 우선 분석한다.

**중요:** PMD-Bot의 에뮬레이터 메모리 접근과 버튼 입력 부분은 독립 PC 앱에 그대로 적용할 수 없으므로, 재사용 가능한 탐색·의사결정 로직과 에뮬레이터 종속 부분을 분리한다.

### 4.3 전투 제거

- 공격·피격·HP 감소·적대 관계를 사용하지 않는다.
- 포켓몬 출현 위치와 종류는 원작 데이터에 따른다.
- 등장 포켓몬과 만나면 우호적 인사 이벤트를 발생시킨다.
- 인사 후 탐험을 재개한다.
- 경로를 막는 포켓몬은 대기·우회·통과 정책으로 처리한다.
- 원작의 전투 관련 데이터는 무리하게 수정하지 않고, 필요한 범위에서 런타임 동작만 비활성화한다.

### 4.4 오류 및 막힘 처리

- 도달 불가능한 아이템에 무한 반복 접근하지 않는다.
- 막힌 경로는 탐색 대상으로부터 일시 제외한다.
- 경로 실패 시 재탐색한다.
- 층 진행이 정지되면 원인을 기록하고 안전한 복구 경로를 사용한다.
- 일정 턴 이상 진행되지 않으면 정의된 실패 처리 정책으로 복구한다.
- 실패를 숨기기 위해 임의의 원작 데이터로 교체하지 않는다.

## 5. 펫의 자율 생활 시스템

### 5.1 상태

```text
HOME
  ↓
PREPARE
  ↓
EXPLORE
  ├─ FRIEND_ENCOUNTER
  ├─ ITEM_EVENT
  ├─ TREASURE_EVENT
  └─ FLOOR_TRANSITION
  ↓
RETURN_HOME
  ↓
REST
  ↓
SLEEP
  ↓
WAKE_UP
  ↓
HOME
```

### 5.2 행동 규칙

- 펫은 독립적인 생활 상태를 보유한다.
- 탐험·귀가·수면·기상은 자율적으로 이루어진다.
- 탐험 목표 던전은 원작 목록에서 선택한다.
- 던전 선택은 해금 상태와 설정된 순환 규칙에 따른다.
- 사용자의 입력 활동이 없어도 탐험 결과는 정상적으로 처리된다.
- 수면 중에는 불필요한 맵 생성과 렌더링을 중단한다.
- 프로그램 재실행 시 저장된 상태에서 복원한다.

### 5.3 원작에 없는 행동

집·귀가·수면 주기와 친구 인사 등의 신규 규칙은 별도의 `PetBehaviorPolicy`에 둔다.

원작 던전 생성·출현 로직에는 직접 결합하지 않는다.

초기에는 간단한 결정적 상태 머신으로 구현한다. LLM, 강화학습, 복잡한 성격·감정 수치 시스템은 추가하지 않는다.

## 6. 사용자 활동 감지

### 6.1 감지 대상

Windows에서 다음 정보만 수집한다.

- 현재 활성 프로그램
- 마지막 키보드·마우스 입력 후 경과 시간
- PC 잠금·해제
- 절전·복귀
- 향후 앱별 작업 완료 이벤트

### 6.2 분류 상태

```text
ACTIVE
DEVELOPING
CREATING
IDLE
AWAY
LOCKED
SUSPENDED
```

`DEVELOPING`과 `CREATING`은 실제 작업 내용 분석 결과가 아닌 활성 프로그램 기반 추정 상태다.

### 6.3 병렬 생활 규칙

- 사용자 활동은 펫의 생활을 직접 조종하지 않는다.
- 개발·창작 작업 중에는 알림과 연출을 줄인다.
- 사용자가 유휴 상태여도 펫의 내부 생활은 유지한다.
- PC 잠금 시 렌더링을 줄이거나 중지한다.
- PC 절전 중에는 실시간 시뮬레이션을 수행하지 않는다.
- 절전 복귀 시 경과 시간을 반영해 생활 상태를 복원한다.
- 실제 작업 완료 이벤트는 향후 별도 어댑터로 추가한다.

### 6.4 개인정보·성능 제약

- 키 입력 내용 기록 금지
- 기본 화면 캡처 금지
- 브라우저 방문 기록 수집 금지
- 로컬 우선 처리
- 불필요한 네트워크 통신 금지
- 활동 기록 영구 저장은 기본적으로 비활성화

## 7. 그래픽·애니메이션

### 7.1 기본 요구사항

- Windows용 작은 플로팅 창
- 기본 창 크기 200×200px
- 100~200px 범위 크기 조정
- 선택적 항상 위 표시
- 사용자 입력 방해 최소화
- 캐릭터·던전·이벤트 표시
- 창 내부의 짧은 이벤트 알림
- 픽셀 아트의 정수 배율 확대 우선
- 원작에 가까운 이동·프레임 타이밍

### 7.2 리소스 재활용

SpriteCollab과 원본 리소스의 구조화된 애니메이션 데이터를 사용한다.

- Walk
- Idle
- Sleep
- Wake
- 필요한 이벤트 모션
- 방향별 애니메이션
- 프레임 지속 시간
- 프레임별 위치 보정

애니메이션 데이터를 일괄 변환하여 런타임용 스프라이트 아틀라스와 메타데이터로 만든다.

캐릭터마다 수동으로 프레임을 잘라 설정하지 않는다.

### 7.3 렌더링 제한

- 렌더링과 시뮬레이션은 분리한다.
- 기본 저주사율 모드를 사용한다.
- 상태 변화가 없을 때 불필요한 화면 갱신을 억제한다.
- 숨김·잠금 상태에서는 렌더링을 중지한다.
- 게임 데이터 추출용 Python 도구는 런타임에 상주시킬 필요가 없다.
- 필요한 타일셋·캐릭터만 메모리에 로드한다.

## 8. 경량화·기술 스택

### 8.1 성능 목표

초기 잠정 목표:

| 항목 | 목표 |
|---|---|
| 비활성 CPU | 평균 0.5% 이하 |
| 일반 실행 CPU | 평균 1% 이하 |
| 상주 메모리 | 30MB 이하 지향 |
| 기본 렌더링 | 15FPS 전후 |
| 동시 프로세스 | 원칙적으로 1개 |
| 클라우드/API | 필수 의존성 없음 |
| 장시간 실행 | 24시간 안정성 검증 |

이는 완료가 보장된 사양이 아니라 **실측을 통해 채택 여부를 결정하는 성능 기준**이다.

### 8.2 기술 선정 원칙

1. 기존 구현을 직접 호출할 수 있는 구조를 우선 검토한다.
2. 엔진 전체 도입과 필요한 모듈만 재사용하는 방식을 비교한다.
3. 가능하면 데이터 변환은 빌드 시점에 처리한다.
4. 런타임에 무거운 툴체인·에뮬레이터·개발 서버를 유지하지 않는다.
5. 웹 렌더링 엔진이 반드시 필요한지 검토한다.
6. 기술 스택 변경은 측정된 이득이 있을 때만 수행한다.

원작 충실도가 저하되는 극단적인 최적화는 하지 않는다. 예를 들어 지도 생성 알고리즘을 임의의 단순 랜덤 맵으로 교체하여 CPU 사용량을 줄이는 것은 허용하지 않는다.

- 원작 대비 누락된 데이터 집계

## 12. Codex 자율 작업 규칙

Codex는 다음 원칙에 따라 사용자의 개입을 최소화한다.

**작업 시작 시**

1. `AGENTS.md`와 `PROJECT_STATE.md`를 확인한다.
2. 현재 단계와 완료 조건을 파악한다.
3. 필요한 기존 코드만 선택적으로 읽는다.
4. 재사용 가능한 코드가 있는지 먼저 확인한다.
5. 작업 계획을 수립하고 실행한다.

**작업 중**

1. 기존 기능을 불필요하게 다시 작성하지 않는다.
2. 선택한 라이브러리의 실제 API를 확인한다.
3. 기능을 구현하면 관련 자동 테스트를 추가한다.
4. 테스트가 실패하면 원인을 조사하고 가능한 범위에서 수정한다.
5. 원작 충실도를 떨어뜨리는 변경은 기록하고 비교한다.
6. 임시 데이터를 완성된 원작 데이터처럼 취급하지 않는다.
7. 기존 정상 기능을 손상시키지 않는다.

**작업 종료 시**

1. 변경 파일과 구현 내용을 요약한다.
2. 테스트 실행 및 통과·실패 결과를 기록한다.
3. 원작과의 차이, 누락 기능, 성능 측정 결과를 보고한다.
4. `PROJECT_STATE.md`를 최신화한다.
5. 필요하면 `docs/DECISIONS.md`에 설계 결정을 남긴다.
6. 작업 로그를 날짜·주제별로 작성한다.
7. Git을 사용하는 경우 변경사항을 확인 가능한 커밋 단위로 정리한다.

**사용자에게 질문할 조건**

다음 경우에만 질문한다.

- 원본 ROM이나 권한 등 사용자가 직접 제공해야 하는 자원이 필요한 경우
- 중요한 게임 경험을 변경하는 설계 선택이 필요한 경우
- 라이선스·배포 범위에 관한 결정이 필요한 경우
- 안전한 자동 해결 방법이 없는 외부 권한·인증 문제

일반적인 라이브러리 선정, 코드 구조, 테스트 방법, 오류 수정은 Codex가 조사하고 판단한다.

외부 저장소 전체 삭제, 기존 데이터 손실, 공개 배포, 라이선스 의무를 변경하는 조치는 별도 승인 없이 진행하지 않는다.

## 13. 라이선스와 자산 처리

오픈소스 코드를 공개했다는 사실이 포켓몬 원작 이미지·데이터의 자유로운 재배포 권한을 의미하지는 않는다.

- 각 코드 저장소의 라이선스를 확인한다.
- GPL 등 카피레프트 의무가 발생하는 통합 방식은 기록한다.
- SpriteCollab의 리소스별 출처·크레딧·이용 조건을 확인한다.
- 팬 제작 리소스의 이용 허락과 원작 저작권 문제를 별도로 취급한다.
- ROM·상업용 게임 자산은 기본적으로 사용자 로컬에서 변환한다.
- 배포 가능 여부가 불명확한 리소스는 앱에 기본 포함하지 않는다.
- 개인용 빌드와 외부 배포용 빌드의 자산 처리 정책을 분리한다.

라이선스 문제를 무시하거나 우회하는 방식으로 프로젝트를 구성하지 않는다.

## 14. 최종 인수 조건

프로젝트 완료 판정은 다음 조건을 모두 만족할 때만 가능하다.

1. Windows에서 독립 실행 가능하다.
2. 작은 플로팅 창에서 포켓몬이 자연스럽게 움직인다.
3. 여러 원작 던전을 자동으로 방문한다.
4. 던전·층별 포켓몬과 아이템이 원작 데이터에 따라 등장한다.
5. 원작의 지도 생성 규칙을 검증된 범위에서 재현한다.
6. 포켓몬과 우호적으로 교류한다.
7. 아이템과 보물을 자동 획득한다.
8. 계단을 통해 다음 층으로 이동한다.
9. 탐험 후 귀가·휴식·수면·기상을 반복한다.
10. 사용자 활동을 감지하고 펫의 독립적인 생활을 유지한다.
11. 장시간 실행이 안정적이다.
12. 리소스 사용량이 실제 측정·보고되어 있다.
13. 데이터 변환 과정에 사용자 수작업이 필요하지 않다.
14. 외부 소스 재활용 범위와 원작 대비 차이가 문서화되어 있다.

**최종 성공 기준:** 사용자가 프로그램을 실행하면, 원작에 가까운 던전 세계를 배경으로 포켓몬이 스스로 생활하고 탐험하며, 사용자의 PC 활동에 자연스럽게 반응한다. 사용자는 개발 중 데이터 추출·규칙 입력·스프라이트 편집을 직접 수행할 필요가 없어야 한다.

## 15. Codex 최초 실행 지시

이 명세를 프로젝트 최상위 개발 기준으로 삼는다.

먼저 Phase 0을 수행하라. 기존 구현을 충분히 조사하기 전까지 원작 던전 생성기·애니메이션 파서·자동 탐색기를 새로 작성하지 않는다.

실제 저장소를 확보하여 코드를 분석하고, 가능한 최소 규모의 실행 PoC로 재활용 가능성을 입증하라.

이후 원작 충실도, 성능, 구현 비용을 비교해 기술 스택을 선정하고 Phase 1부터 순차적으로 개발한다.

각 단계에서는 필요한 조사·구현·자동 테스트·오류 수정을 스스로 수행하고, 검증 가능한 완료 조건을 충족한 경우 다음 단계로 진행한다.

작업에 필요한 원본 ROM, 외부 권한, 중요한 사용자 결정이 없다면 매번 승인을 요청하지 말고 진행한다. 단, 도구 실행 환경이 실제로 허용하는 권한을 넘어서지는 않는다.

사용자가 직접 수행해야 할 작업은 **원작 데이터 사용을 위한 적법한 파일 제공, 최종 시각적·사용성 평가, 중요한 제품 방향 결정**으로 최소화한다.
